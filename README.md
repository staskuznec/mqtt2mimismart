# mqtt2mimismart

Шлюз между шиной MQTT и умным домом **MimiSmart**. Устройства публикуют свои
состояния в брокер, шлюз раскладывает их по элементам умного дома, а нажатия из
приложения переводит обратно в команды устройствам.

Настраивается целиком в браузере: конфигов на диске нет, рядом с бинарником
лежит только файл базы.

```
   устройства              шлюз                     умный дом
  ┌──────────┐        ┌─────────────┐            ┌──────────────┐
  │ Shelly   │──MQTT─▶│  связки     │──протокол─▶│  элементы    │
  │ и другие │◀───────│  и шаблоны  │◀───SHS─────│  MimiSmart   │
  └──────────┘        └──────┬──────┘            └──────────────┘
                             │
                      веб-интерфейс
```

## Установка

Одной командой на сервере статистики:

```bash
curl -fsSL https://github.com/staskuznec/mqtt2mimismart/releases/latest/download/install.sh | sudo sh
```

Скрипт делает всё: ставит бинарник под вашу архитектуру, при необходимости
поднимает MQTT-брокер, настраивает веб-сервер, добавляет вкладку «MQTT» в
панель MimiSetup и запускает службу.

По ходу он спросит две вещи. Первая — нужны ли пароли на брокере:

```
Как настроить доступ к брокеру?
  1 — с паролями (рекомендую)
  2 — без паролей

Пароль для устройств: ••••••
Пароль для нашего шлюза: ••••••
```

Пароли стоит завести, если в сети бывают гости или чужие устройства: по этой
шине ходят команды, щёлкающие нагрузку на 230 В. В изолированной сети можно
обойтись без них.

Вторая — открывать ли шлюз рядом с панелью умного дома. Если согласиться, он
будет доступен по `http://сервер/mqtt/`, а не отдельным портом.

В конце скрипт напечатает, что именно вводить в настройках шлюза и в настройках
каждого устройства.

### Обновление

Та же команда. База и настройки лежат отдельно, в `/var/lib/mqtt2mimismart`, и
не трогаются. Предыдущий бинарник сохраняется рядом — если что-то пойдёт не так,
откат в одно движение:

```bash
mv /opt/mqtt2mimismart/mqtt2mimismart.old /opt/mqtt2mimismart/mqtt2mimismart
systemctl restart mqtt2mimismart
```

О новых версиях шлюз сообщает сам, на странице «Обзор», и там же ставит их
кнопкой «Обновить» — вопросов она не задаёт и обновляет всё разом: и сам шлюз,
и вкладку в панели умного дома. Занимает это несколько секунд, пока шлюз
перезапускается.

Автоматически он не обновляется: демон, управляющий светом в доме, не должен
решать за вас, когда ему перезапуститься. Кнопку нажимаете вы.

### Без установщика

```bash
make build          # под текущую машину
make build-armv7    # под ARMv7
```

Готовый файл кладётся в `exe/`. Запуск:

```bash
./mqtt2mimismart --addr 0.0.0.0:8080 --db ./gateway.db
```

Флагов немного, и все — про то, что нельзя хранить в самой базе:

| Флаг | Что задаёт |
|------|------------|
| `--addr` | адрес веб-интерфейса, по умолчанию `127.0.0.1:8080` |
| `--db` | путь к файлу базы |
| `--base-path` | подкаталог, если шлюз стоит за веб-сервером: `/mqtt` |
| `--profiles` | каталог с профилями устройств |
| `--log-level` | `debug`, `info`, `warn`, `error` |

## Первые шаги

**1. Настройки.** Откройте шлюз и заполните два блока: адрес брокера и адрес
сервера умного дома с ключом. Ключ берётся из настроек сервера статистики и
должен быть длиной ровно 16, 24 или 32 байта — это требование AES.

Путь к `logic.xml` указывать не нужно: описание дома приходит от сервера при
подключении, поэтому список элементов всегда соответствует тому серверу, с
которым шлюз работает на самом деле.

**2. Устройство.** Переведите Shelly на MQTT, затем на странице «Устройства»
нажмите «Добавить». Выберите модель, префикс топиков — он подставится из того,
что видно на шине, — и назначьте элементы умного дома.

Роль без выбранного элемента пропускается: не нужна мощность — не назначайте
её, и связок под неё не появится.

**3. Проверка.** Щёлкните лампу в приложении умного дома — реле должно
сработать. Нажмите кнопку на самом реле — состояние вернётся в приложение.

## Разделы интерфейса

| Раздел | Что там |
|--------|---------|
| Обзор | состояние обоих соединений, счётчики, сообщение о новой версии |
| Топики | всё, что реально ходит по шине, разложенное по устройствам: болтливое устройство приезжает свёрнутым, длинное значение — началом строки |
| Устройства | развёрнутые из шаблонов; здесь же они настраиваются заново |
| Связки | что и куда переводит шлюз, с последними значениями и ошибками |
| Элементы | дерево умного дома из `logic.xml`, кнопка «перечитать» и заведение элементов под профиль |
| Профили | описания моделей: редактор с проверкой и справка по формату |
| Настройки | брокер и сервер умного дома |

## Связки

Связка — это одно правило: взять значение из топика и положить в элемент, либо
наоборот. Двусторонняя привязка показана одной строкой, но под капотом их две:
у направлений разные счётчики и своё включение, и когда команда не уходит, а
состояние приходит, это должно быть видно раздельно.

Заводить связки по одной обычно не нужно — для этого есть шаблоны. Но если
устройство нетиповое, на странице «Топики» рядом с нужным топиком есть кнопка
«Связать»: топик подставится сам, элемент выбирается из списка с настоящими
именами и областями.

### Панель «Проба»

В редакторе связки есть проба: вводите пример сообщения и видите, во что оно
превратится и **какие байты уйдут на провод**. Считает её тот же код, который
потом и отправит значение, поэтому расхождение между пробой и работой
невозможно.

Именно здесь ловится самая дорогая ошибка проекта — про неё ниже.

### Таблица значений

Устройство говорит своими словами, элемент умного дома — своими. Таблица
переводит: по строке на пару, `ключ = значение`.

```
on = 1
off = 0
overpower = 1
```

Ключом может быть и порог — для чисел точного совпадения не бывает. Уровень
сигнала WiFi приходит как `-73`, а на панели хочется слово:

```
<=-90 = нет сигнала
<=-80 = плохой
<=-70 = средний
<=-60 = хороший
*     = отличный
```

Пороги `<=` проверяются по возрастанию, `>=` — по убыванию: срабатывает
ближайший, а не первый попавшийся. Звёздочка — то, что не попало ни в один
диапазон; она работает только вместе с порогами и только для чисел. Слово
`offline` порогам сравнивать не с чем, и подменять его звёздочкой нельзя:
авария выглядела бы как отличный сигнал. Точное совпадение сильнее любого
порога.

### Формы значения

Протокол умного дома передаёт числа как fixed-point 8.8, и форма значения
зависит от типа элемента, а не от устройства:

| Форма | Для чего | Пример на проводе |
|-------|----------|-------------------|
| один байт | лампы, шторы, скрипты, клапаны, датчики двери | `01` |
| датчик 8.8 | температура, влажность, освещённость | `80 2a` = 42.5 |
| текст | всё, что не влезает в 8.8: ватты, кВт·ч, вольты | `41.2 Вт` |

**Перепутать байт с датчиком — самая частая и самая обидная ошибка.** У
однобайтовых элементов состояние занимает ровно один байт. Если отправить
такому элементу значение датчика, единица уедет как `00 01`: младший байт
нулевой, и лампа останется выключенной. Выключение при этом «работает», потому
что ноль даёт нули в обоих байтах — и выглядит это как случайные пропажи
статуса.

Шлюз подсказывает форму по типу элемента из `logic.xml`, а проба показывает
байты. Обе защиты появились именно из-за этой ошибки.

## Профили устройств

Профиль описывает, какие связки нужны модели и какие элементы под них назначить.
Развернуть десяток связок — одно действие.

Лежат они обычными файлами:

```
/home/sh2/mqtt/profiles/shelly25-relay.json
```

Каталог задаётся флагом `--profiles`. Туда можно положить свой файл, скопировать
профиль с другого объекта или открыть существующий редактором — а можно
править прямо в вебе: в разделе «Профили» есть редактор с подсветкой и
проверкой по мере набора, вплоть до номера строки с ошибкой.

В самом репозитории профили лежат в каталоге `profiles/` — это данные, а не
код, и править их так же просто, как открыть файл.

**Поставляемый профиль остаётся эталонным.** Правка такого профиля — хоть в
вебе, хоть редактором на диске — сохраняется отдельным файлом
`<ключ>.local.json`, а сам профиль возвращается к поставляемому виду и
обновляется дальше вместе со шлюзом. Устройства, заведённые по правленому
профилю, переезжают на копию: связки у них уже работают, речь только о том,
что откроется в форме устройства.

Раньше правленый файл оставался на месте, и исправления шли мимо него: на
объекте профиль годами оставался таким, каким его однажды подкрутили, а о новых
ролях узнать было неоткуда. Теперь и правка цела, и эталон свежий.

**Копия у профиля одна.** Дальше правится она, а не эталон: редактор говорит об
этом, открывая поставляемый профиль, и не даёт сохранить вторую копию — иначе
каждая правка плодила бы файл, и через месяц в каталоге лежало бы десять «моих»
`shelly25-relay`, из которых не разобрать, какой рабочий. Исключение одно: файл
эталона правят редактором прямо на диске, когда копия уже есть. Спросить в этот
момент некого, и правка ложится рядом — `<ключ>.local-2.json`: затереть чужую
работу хуже, чем оставить лишний файл.

Со шлюзом поставляются пять семейств.

**Shelly Gen1:** 1, 1PM, Plug и Plug S, Dimmer 1/2, 2.5 в режимах реле и
роллера, батарейные H&T, Flood, Door/Window 2 и Button1.

**Shelly Plus и Pro (Gen2+):** Plus 1, Plus 1PM, Plus 2PM в режимах реле и
ролеты, Plus Plug S, Plus i4, Pro 4PM, Plus H&T. На устройстве надо включить
«Generic status update over MQTT»: без этой галочки Gen2 состояние не
публикует вовсе, и связки останутся пустыми.

У всех сетевых профилей есть два диагностических элемента: «на связи» и
«уровень сигнала». Оба текстовые: элемент показывает `онлайн`/`офлайн` и
`плохой`/`нормальный`/`хороший` словом — лампа, которую надо помнить как
читать, для диагностики годится хуже. Уровень собирается порогами из таблицы
значений, каждое семейство берёт его из своего топика:

| Семейство | Откуда | Шкала |
|-----------|--------|-------|
| Shelly Gen1 | `info`, поле `wifi_sta.rssi` | dBm, порог `-80` |
| Shelly Gen2+ | `status/wifi`, поле `rssi` | dBm, порог `-80` |
| Tasmota | `tele/<имя>/STATE`, поле `Wifi.Signal` | dBm, порог `-80` |
| Zigbee2MQTT | состояние устройства, поле `linkquality` | LQI, порог `50` |

Мигающее реле почти всегда объясняется именно этим элементом: ниже `-80 dBm`
команды начинают теряться, и видно это раньше, чем жалобы. У Zigbee шкала
другая: LQI — величина относительная, у разных координаторов своя, и сравнивать
по ней имеет смысл устройства одной сети между собой.

**Tasmota:** реле на один, два и четыре канала, розетка с измерением, датчики
температуры и влажности. Это Sonoff, NOUS, Gosund, BlitzWolf, перепрошитые
Tuya и любая самоделка на ESP.

**Zigbee2MQTT:** профили на класс устройства, а не на модель — лампа,
выключатель, розетка с измерением, датчики температуры, движения, открытия,
протечки и кнопка. Одним профилем закрываются тысячи железок, включая
батарейные датчики, которых у Shelly нет.

**МикроАрт МАП:** инвертор с агентом на «Малине», два профиля по тому, что
инвертор реально публикует. Dominator (и всякий МАП, у которого работает
монитор батарей) отдаёт разделы `map`, `bat` и `mppt` — это батарея, солнце и
ветер вдобавок к сети, нагрузке, температурам, режиму и ошибкам. Hybrid и Sin
Pro без монитора публикуют один `map`: заряда в процентах, ёмкости и
температуры АКБ там не существует, и профиль под них короче на два десятка
ролей — чтобы не назначать элементы показаниям, которые не придут никогда.
Ролей в обоих много намеренно: агент публикует всё, что отдаёт инвертор, а
роль без элемента в связку не разворачивается. Связки только на вход: агент
отдаёт показания, а управлять МАП по шине не даёт. Каждый инвертор заводится
своим корнем топиков (`microart/inv1`, `microart/inv2`).

При первом запуске профили раскладываются в каталог, а дальше принадлежат вам.
Обновление шлюза добавляет новые модели и подтягивает исправления в те файлы,
которых вы не касались: рядом лежит `.bundled.json` с отпечатками того, что
клал шлюз, и файл, совпадающий с отпечатком, считается его собственным.
Файл, который вы правили, не трогается никогда — но если исправление вышло
именно для него, в журнале появится предупреждение. Удалили поставляемый — он
вернётся при следующем запуске, потому что едет в бинарнике.

**Профиль разворачивается в связки один раз.** Обновившийся профиль сам по себе
ничего не меняет в устройствах, которые уже настроены: связки живут в базе
своей жизнью, иначе правка профиля переписывала бы рабочий объект без спроса.
Чтобы применить исправление к настроенному устройству, откройте его на странице
«Устройства», нажмите «настроить» и сохраните — связки соберутся заново.

Единицы во всех профилях приведены к одному виду: мощность и напряжение без
знаков после запятой (`41 Вт`, `234 В`), энергия с одним знаком в киловаттах
(`3.5 кВт`), ток с двумя знаками (`0.34 А`), заряд, ёмкость и освещённость
целыми (`87 %`, `178 А·ч`, `152 лк`).

**Профиль — это данные, а не код.** Новая модель добавляется файлом, без
пересборки и без релиза. Описание формата — на странице «Профили»: таблицы
полей, полный пример и места, на которых легко обжечься.

## Что стоит знать

**Опроса по таймеру нет.** Состояния приходят сами: устройства публикуют
изменения в брокер, а сервер умного дома шлёт свои. Полный снимок состояний
запрашивается только при подключении и раз в несколько секунд для поддержания
связи — и наружу он не транслируется, иначе каждый старт щёлкал бы всеми реле
на объекте.

**Элементы под профиль заводит шлюз, а вставляете их вы.** На инверторе полсотни
показаний, и придумывать адрес каждому руками — работа на вечер с тихой ошибкой
в конце: связка пишет в чужой элемент. В форме устройства есть галочка «создать
элементы в умном доме»: она открывает выбор модуля (CM) из тех, что уже есть в
`logic.xml`, области и первого `sub-id`, а в каждой роли появляется вариант
«создать элемент». Шлюз подбирает свободные адреса — занятые пропускает, — сразу
разворачивает связки и показывает готовый кусок `logic.xml` с комментарием,
откуда каждый элемент получает значение. Вставляете его через MimiSetup,
перезагружаете умный дом и нажимаете «перечитать» — связки оживают. Пока
элементов нет, они помечены «нет элемента», и это ожидаемо.

То же самое отдельно от устройства — на странице «Элементы» → «Завести элементы
под профиль».

Записывать `logic.xml` шлюз не пытается: файл принадлежит серверу умного дома, и
юнит открывает домашний каталог только на чтение. Битый `logic.xml` означает
мёртвый объект целиком, а не одну неработающую связку.

**В несуществующий элемент шлюз не пишет.** Связка живёт в базе шлюза и
переживает правку `logic.xml`: элемент удалили или перенумеровали, а связка
осталась. Отправка при этом не ошибается — пакет уходит на адрес, которого нет,
— и настоящая беда начинается, когда по освободившемуся адресу заводят другой
элемент: туда поедут чужие значения. Поэтому перед записью адрес сверяется с
описанием дома, а связка помечается на странице «Связки» как «нет элемента».
Пока описание не приехало, проверка пропускает всё: обрыв связи с умным домом
не повод останавливать исправный объект.

**Описание дома приезжает один раз — в рукопожатии.** Пока соединение живо,
сервер его не переприсылает, поэтому добавленный элемент шлюз сам не увидит.
Для этого на странице «Элементы» есть «перечитать»: она здоровается заново.

**Сохранённые значения подтягиваются при каждой правке связок.** Брокер отдаёт
`retain` один раз — в момент подписки, то есть до того, как связку завели.
Поэтому после развёртывания устройства или правки связки шлюз подписывается
заново и просит всё сохранённое ещё раз: иначе новая связка стояла бы пустой
до следующей публикации, а редкий топик вроде доступности инвертора молчит
часами.

**Петли не возникает.** Записали в лампу — сервер вернул эту же запись
событием — шлюз узнаёт в ней своё и наружу не пускает. Отдельно отсеиваются
повторы: одно и то же значение не отправляется дважды. А вот нажатие проходит
всегда: нажали дважды — переключить надо дважды.

**Нажатие уезжает абсолютной командой.** Умный дом на нажатие лампы присылает
«переключить», и раньше это слово так и уходило устройству. Команда
относительная, а на слабом WiFi одна потерянная публикация уводит фазу
навсегда: элемент показывает «включено», реле выключено, и следующее нажатие
срабатывает наоборот. Gen1 публикует состояние только при изменении и сам
ничего не исправит — на объекте это выглядит как «канал слушается через раз».
Поэтому шлюз разворачивает нажатие по последнему состоянию, о котором
отчиталось устройство: было включено — уедет «выключить». Своё же нажатие в это
состояние не записывается: пока устройство молчит, повторное нажатие повторяет
ту же команду, и потерянная публикация чинится вторым нажатием. Если состояния
ещё нет или устройство не понимает абсолютных команд — уходит переключение, как
раньше.

**Порядок сообщений сохраняется.** Два состояния одного реле, пришедшие подряд,
разбираются в том порядке, в каком их прислал брокер. Иначе отсев повторов
запомнил бы устаревшее значение и отбросил правильное, а элемент залип бы до
следующей публикации.

**Сохранённая команда опасна.** Флаг `retain` на командном топике заставит
брокер отдать команду устройству при следующем его подключении, и реле щёлкнет
само. Шлюз это запрещает проверкой. Для показаний наружу `retain`, наоборот,
уместен — там он и разрешён.

## Устройство проекта

```
cmd/gateway/             точка входа
internal/app/            сборка демона из частей
internal/mqtt/           брокер и снифер шины
internal/shs/            соединение с умным домом, поверх shClientMimismart
internal/link/           ядро: сопоставление топиков, преобразование, движок
internal/devtmpl/        работа с профилями устройств
profiles/                сами профили: описания моделей
internal/logic/          разбор logic.xml
internal/store/          SQLite: настройки, связки, устройства, шаблоны
internal/web/            веб-интерфейс, вшит через go:embed
internal/update/         проверка новых версий
deploy/                  юнит systemd и вкладка для панели MimiSetup
```

Клиент протокола SHS вынесен в отдельную библиотеку
[shClientMimismart](https://github.com/staskuznec/shClientMimismart).

Проверки:

```bash
make test    # gofmt, go vet, go test -race
```

## Сколько раз ставили и обновляли

GitHub считает скачивания файлов релиза, и по ним видно картину:

```bash
sh tools/stats.sh
```

Скачивания `install.sh` — запуски установщика, бинарника — установщик плюс
обновления кнопкой в вебе; разница между ними и есть обновления. Обращения к
`raw.githubusercontent.com` и проверки версии GitHub не учитывает вовсе,
поэтому установщик и качается ссылкой на релиз.

Учёт грубый: одна установка на трёх машинах считается тремя, а повторная
попытка после неудачи — ещё одной. Ничего точнее без своей телеметрии не
выйдет, а её в шлюзе нет и не планируется.
