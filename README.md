# mqtt2mimismart

Шлюз между шиной MQTT и умным домом **MimiSmart**. Устройства публикуют свои
состояния в брокер, шлюз раскладывает их по элементам умного дома, а нажатия из
приложения переводит обратно в команды устройствам.

Настраивается целиком в браузере: конфигов на диске нет, рядом с бинарником
лежит только файл базы.

```
   устройства              шлюз                     умный дом
  ┌──────────┐        ┌─────────────┐            ┌──────────────┐
  │ Shelly   │──MQTT─▶│  связки     │──протокол─▶│  элементы    │
  │ и другие │◀───────│  и шаблоны  │◀───SHS─────│  MimiSmart   │
  └──────────┘        └──────┬──────┘            └──────────────┘
                             │
                      веб-интерфейс
```

## Установка

Одной командой на сервере статистики:

```bash
curl -fsSL https://github.com/staskuznec/mqtt2mimismart/releases/latest/download/install.sh | sudo sh
```

Скрипт делает всё: ставит бинарник под вашу архитектуру, при необходимости
поднимает MQTT-брокер, настраивает веб-сервер, добавляет вкладку «MQTT» в
панель MimiSetup и запускает службу.

По ходу он спросит две вещи. Первая — нужны ли пароли на брокере:

```
Как настроить доступ к брокеру?
  1 — с паролями (рекомендую)
  2 — без паролей

Пароль для устройств: ••••••
Пароль для нашего шлюза: ••••••
```

Пароли стоит завести, если в сети бывают гости или чужие устройства: по этой
шине ходят команды, щёлкающие нагрузку на 230 В. В изолированной сети можно
обойтись без них.

Вторая — открывать ли шлюз рядом с панелью умного дома. Если согласиться, он
будет доступен по `http://сервер/mqtt/`, а не отдельным портом.

В конце скрипт напечатает, что именно вводить в настройках шлюза и в настройках
каждого устройства.

### Обновление

Та же команда. База и настройки лежат отдельно, в `/var/lib/mqtt2mimismart`, и
не трогаются. Предыдущий бинарник сохраняется рядом — если что-то пойдёт не так,
откат в одно движение:

```bash
mv /opt/mqtt2mimismart/mqtt2mimismart.old /opt/mqtt2mimismart/mqtt2mimismart
systemctl restart mqtt2mimismart
```

О новых версиях шлюз сообщает сам, на странице «Обзор», и там же ставит их
кнопкой «Обновить» — вопросов она не задаёт и обновляет всё разом: и сам шлюз,
и вкладку в панели умного дома. Занимает это несколько секунд, пока шлюз
перезапускается.

Автоматически он не обновляется: демон, управляющий светом в доме, не должен
решать за вас, когда ему перезапуститься. Кнопку нажимаете вы.

### Без установщика

```bash
make build          # под текущую машину
make build-armv7    # под ARMv7
```

Готовый файл кладётся в `exe/`. Запуск:

```bash
./mqtt2mimismart --addr 0.0.0.0:8080 --db ./gateway.db
```

Флагов немного, и все — про то, что нельзя хранить в самой базе:

| Флаг | Что задаёт |
|------|------------|
| `--addr` | адрес веб-интерфейса, по умолчанию `127.0.0.1:8080` |
| `--db` | путь к файлу базы |
| `--base-path` | подкаталог, если шлюз стоит за веб-сервером: `/mqtt` |
| `--profiles` | каталог с профилями устройств |
| `--log-level` | `debug`, `info`, `warn`, `error` |

## Первые шаги

**1. Настройки.** Откройте шлюз и заполните два блока: адрес брокера и адрес
сервера умного дома с ключом. Ключ берётся из настроек сервера статистики и
должен быть длиной ровно 16, 24 или 32 байта — это требование AES.

Путь к `logic.xml` указывать не нужно: описание дома приходит от сервера при
подключении, поэтому список элементов всегда соответствует тому серверу, с
которым шлюз работает на самом деле.

**2. Устройство.** Переведите Shelly на MQTT, затем на странице «Устройства»
нажмите «Добавить». Выберите модель, префикс топиков — он подставится из того,
что видно на шине, — и назначьте элементы умного дома.

Роль без выбранного элемента пропускается: не нужна мощность — не назначайте
её, и связок под неё не появится.

**3. Проверка.** Щёлкните лампу в приложении умного дома — реле должно
сработать. Нажмите кнопку на самом реле — состояние вернётся в приложение.

## Разделы интерфейса

| Раздел | Что там |
|--------|---------|
| Обзор | состояние обоих соединений, счётчики, сообщение о новой версии |
| Топики | всё, что реально ходит по шине, разложенное по устройствам |
| Устройства | развёрнутые из шаблонов; здесь же они настраиваются заново |
| Связки | что и куда переводит шлюз, с последними значениями и ошибками |
| Элементы | дерево умного дома из `logic.xml` |
| Профили | описания моделей: редактор с проверкой и справка по формату |
| Настройки | брокер и сервер умного дома |

## Связки

Связка — это одно правило: взять значение из топика и положить в элемент, либо
наоборот. Двусторонняя привязка показана одной строкой, но под капотом их две:
у направлений разные счётчики и своё включение, и когда команда не уходит, а
состояние приходит, это должно быть видно раздельно.

Заводить связки по одной обычно не нужно — для этого есть шаблоны. Но если
устройство нетиповое, на странице «Топики» рядом с нужным топиком есть кнопка
«Связать»: топик подставится сам, элемент выбирается из списка с настоящими
именами и областями.

### Панель «Проба»

В редакторе связки есть проба: вводите пример сообщения и видите, во что оно
превратится и **какие байты уйдут на провод**. Считает её тот же код, который
потом и отправит значение, поэтому расхождение между пробой и работой
невозможно.

Именно здесь ловится самая дорогая ошибка проекта — про неё ниже.

### Формы значения

Протокол умного дома передаёт числа как fixed-point 8.8, и форма значения
зависит от типа элемента, а не от устройства:

| Форма | Для чего | Пример на проводе |
|-------|----------|-------------------|
| один байт | лампы, шторы, скрипты, клапаны, датчики двери | `01` |
| датчик 8.8 | температура, влажность, освещённость | `80 2a` = 42.5 |
| текст | всё, что не влезает в 8.8: ватты, кВт·ч, вольты | `41.2 Вт` |

**Перепутать байт с датчиком — самая частая и самая обидная ошибка.** У
однобайтовых элементов состояние занимает ровно один байт. Если отправить
такому элементу значение датчика, единица уедет как `00 01`: младший байт
нулевой, и лампа останется выключенной. Выключение при этом «работает», потому
что ноль даёт нули в обоих байтах — и выглядит это как случайные пропажи
статуса.

Шлюз подсказывает форму по типу элемента из `logic.xml`, а проба показывает
байты. Обе защиты появились именно из-за этой ошибки.

## Профили устройств

Профиль описывает, какие связки нужны модели и какие элементы под них назначить.
Развернуть десяток связок — одно действие.

Лежат они обычными файлами:

```
/home/sh2/mqtt/profiles/shelly25-relay.json
```

Каталог задаётся флагом `--profiles`. Туда можно положить свой файл, скопировать
профиль с другого объекта или открыть существующий редактором — а можно
править прямо в вебе: в разделе «Профили» есть редактор с подсветкой и
проверкой по мере набора, вплоть до номера строки с ошибкой.

В самом репозитории профили лежат в каталоге `profiles/` — это данные, а не
код, и править их так же просто, как открыть файл.

Со шлюзом поставляются модели семейства Gen1: Shelly 1, 1PM, Plug и Plug S,
Dimmer 1/2, 2.5 в режимах реле и роллера, а также батарейные H&T, Flood,
Door/Window 2 и Button1. При первом запуске они раскладываются в каталог, а
дальше принадлежат вам: обновление шлюза добавляетновые модели, но не трогает
изменённые вами файлы. Удалили поставляемый — он вернётся при следующем
запуске, потому что едет в бинарнике.

Единицы во всех профилях приведены к одному виду: мощность и напряжение без
знаков после запятой (`41 Вт`), энергия с одним знаком в киловаттах
(`3.5 кВт`).

**Профиль — это данные, а не код.** Новая модель добавляется файлом, без
пересборки и без релиза. Описание формата — на странице «Профили»: таблицы
полей, полный пример и места, на которых легко обжечься.

## Что стоит знать

**Опроса по таймеру нет.** Состояния приходят сами: устройства публикуют
изменения в брокер, а сервер умного дома шлёт свои. Полный снимок состояний
запрашивается только при подключении и раз в несколько секунд для поддержания
связи — и наружу он не транслируется, иначе каждый старт щёлкал бы всеми реле
на объекте.

**Петли не возникает.** Записали в лампу — сервер вернул эту же запись
событием — шлюз узнаёт в ней своё и наружу не пускает. Отдельно отсеиваются
повторы: одно и то же значение не отправляется дважды. А вот нажатие проходит
всегда: нажали дважды — переключить надо дважды.

**Сохранённая команда опасна.** Флаг `retain` на командном топике заставит
брокер отдать команду устройству при следующем его подключении, и реле щёлкнет
само. Шлюз это запрещает проверкой. Для показаний наружу `retain`, наоборот,
уместен — там он и разрешён.

## Устройство проекта

```
cmd/gateway/             точка входа
internal/app/            сборка демона из частей
internal/mqtt/           брокер и снифер шины
internal/shs/            соединение с умным домом, поверх shClientMimismart
internal/link/           ядро: сопоставление топиков, преобразование, движок
internal/devtmpl/        работа с профилями устройств
profiles/                сами профили: описания моделей
internal/logic/          разбор logic.xml
internal/store/          SQLite: настройки, связки, устройства, шаблоны
internal/web/            веб-интерфейс, вшит через go:embed
internal/update/         проверка новых версий
deploy/                  юнит systemd и вкладка для панели MimiSetup
```

Клиент протокола SHS вынесен в отдельную библиотеку
[shClientMimismart](https://github.com/staskuznec/shClientMimismart).

Проверки:

```bash
make test    # gofmt, go vet, go test -race
```

## Сколько раз ставили и обновляли

GitHub считает скачивания файлов релиза, и по ним видно картину:

```bash
sh tools/stats.sh
```

Скачивания `install.sh` — запуски установщика, бинарника — установщик плюс
обновления кнопкой в вебе; разница между ними и есть обновления. Обращения к
`raw.githubusercontent.com` и проверки версии GitHub не учитывает вовсе,
поэтому установщик и качается ссылкой на релиз.

Учёт грубый: одна установка на трёх машинах считается тремя, а повторная
попытка после неудачи — ещё одной. Ничего точнее без своей телеметрии не
выйдет, а её в шлюзе нет и не планируется.
