# Shelly 2.5 → MimiSmart

Мост между умным домом **MimiSmart** и реле **Shelly 2.5 (SHSW-25)**: умный дом
управляет каналами реле и получает обратно их состояние, мощность, энергию,
напряжение и температуру.

Физические выключатели в само реле не заводятся — они подключены ко входам
умного дома и привязываются к элементам его собственной логикой. Реле работает
как исполнитель, доступный по сети.

## Как это устроено

Три части, каждая со своей ролью.

**Скрипт MimiSmart** (`script/Shelly_2.5.txt`) живёт в умном доме. Он ловит
нажатия по лампам, собирает текстовую команду и кладёт её статусом в
элемент-исполнитель. По таймеру он же отправляет команду опроса.

**Элемент-исполнитель** — это `<item type="script">` в логике умного дома,
который запускает бинарник и передаёт ему полученный текст HEX-строкой в
аргументе.

**Бинарник** (`cmd/shelly-2.5`) живёт доли секунды: разбирает команду, ходит к
реле по HTTP, при опросе раскладывает ответ по элементам умного дома через
`shClient` и завершается.

```
нажатие по лампе
      ↓
скрипт MimiSmart ──setStatus──▶ элемент-исполнитель ──запуск──▶ бинарник
                                                                    │
                                                          HTTP REST │
                                                                    ▼
                                                              Shelly 2.5
таймер опроса                                                       │
      ↓                                                             │
скрипт MimiSmart ──setStatus──▶ исполнитель ──запуск──▶ бинарник ◀──┘
                                                            │
элементы умного дома ◀────────── shClient (протокол SHS) ◀───┘
```

Состояние в умный дом попадает **только через опрос**. После команды бинарник
ничего не пишет: иначе получались бы две записи подряд, от команды и от опроса,
и элемент в интерфейсе дёргался бы при малейшем расхождении. Благодаря этому
изменение с любой стороны — из веб-интерфейса реле, кнопкой на устройстве, по
расписанию — доезжает одинаково.

## Формат команды

```
[user:pass@]host|action|channel[|цель=id:subid]...
```

| Поле | Значение |
|------|----------|
| `host` | IP реле; учётные данные Basic Auth пишутся как `user:pass@ip` |
| `action` | `on`, `off`, `toggle`, `status` |
| `channel` | `0` (выход O1) или `1` (выход O2); для опроса можно не указывать, если у целей есть номер |
| цели | куда положить результат |

Цели канала — `state`, `power`, `energy`, `overpower`. К ним можно приписать
номер канала (`state0`, `power1`), тогда одна команда покрывает оба выхода.
Цели устройства — `voltage`, `temp`, `overtemp`, номеров не имеют.

Примеры:

```
192.168.20.222|on|0
shadow:secret@192.168.20.222|toggle|1|state=563:57
192.168.20.222|status||state0=563:57|power0=563:120|state1=563:58|voltage=563:124|temp=563:125
```

Позиция аргумента с HEX-командой определяется автоматически: бинарник берёт
первый аргумент, который декодируется и разбирается в осмысленную команду.
Закрепить её можно переменной `SHELLY_ARG_INDEX`.

Получить HEX для ручной проверки:

```bash
printf '192.168.20.222|status|' | xxd -p | tr -d '\n'
```

Перенос строки убирать обязательно: `xxd -p` разбивает вывод каждые 60
символов, и подстановка `$(...)` разложит его на несколько аргументов.

## Форматы значений

Это самая неочевидная часть, и на ней проще всего ошибиться.

Протокол SHS передаёт числа датчиков как **fixed-point 8.8**: `uint16(v * 256)`,
то есть представимый диапазон примерно ±128. Поэтому значения раскладываются по
трём формам, и бинарник выбирает форму сам, по смыслу цели.

| Величина | Форма | Как выглядит |
|----------|-------|--------------|
| состояние реле, перегрузка, перегрев | один сырой байт | `0` или `1` |
| мощность | текст | `41.2 Вт` |
| энергия | текст | `3.52 кВ` |
| напряжение | текст | `231.4 В` |
| температура | датчик 8.8 | `42.3` |

**Состояние обязано уходить одним байтом.** Лампа хранит его в одном байте, а
значение датчика для единицы даёт на проводе `00 01` — первый байт нулевой, и
лампа остаётся выключенной. При этом выключение «работает», потому что ноль
даёт нули в обоих байтах: получается асимметрия, которая долго выглядит как
случайные пропажи статуса.

**Ватты, киловатт-часы и 230 В в число не помещаются** и потому уходят текстом.
Текст снимает ограничение диапазона полностью.

## Подключение реле

| Клемма | Назначение |
|--------|------------|
| `L` / `N` | питание 110–230 В AC (или `+`/`-` для 24–60 В DC) |
| `O1` | нагрузка канала 0, до 10 A |
| `O2` | нагрузка канала 1, до 10 A |
| `SW1` / `SW2` | входы выключателей — **не подключены** |

Вторые концы нагрузок идут на `N`. Входы оставлены пустыми: реле управляется
только по сети. При желании можно дополнительно выставить на реле
`btn_type=detached`, чтобы вход гарантированно не переключал выход:

```bash
curl "http://192.168.20.222/settings/relay/0?btn_type=detached"
```

Устройство должно быть в режиме `relay`, а не `roller` — иначе эндпоинты
`/relay/*` просто не работают.

> ⚠️ 230 В. Монтаж выполняет квалифицированный электрик при обесточенной линии.

## Установка скрипта в умный дом

Лампы создаются **заранее и вручную** — скриптом их завести нельзя. Объявляются
они атрибутом `hw` в датчике 98:

```
hw="virtual:56-LLL"
```

Здесь `56` — первый свободный sub-id, увеличенный на 8, каждая буква `L`
добавляет одну лампу. Создадутся 56, 57 и 58. **Адрес, кратный восьми, работать
корректно не будет** — то есть 56 использовать нельзя, берутся 57 и 58. Для
одного реле нужны две рабочие лампы, поэтому трёх объявленных достаточно.

Дальше импортируется `script/Shelly_2.5.txt`. Он создаст шесть датчиков —
мощность и энергию на каждый канал, напряжение и температуру на устройство, — а
лампы попросит выбрать из списка. В полях указываются адрес элемента-исполнителя,
адрес реле, период опроса и признак отладки.

## Конфиг

Ищется в таком порядке: путь из `SHELLY_CONFIG`, затем файл с именем бинарника
рядом с ним (`94.sh` → `94.yaml`), затем `shelly.yaml` там же.

Реле в конфиге не описываются: их адреса, учётные данные и адреса элементов
приходят в команде. Остаётся только подключение к серверу умного дома:

```yaml
mimismart:
  addr: "127.0.0.1:9001"
  key: "0123456789abcdef"   # ровно 16, 24 или 32 байта
  mac: ""

logging:
  level: error              # debug | info | warn | error
  format: text

runtime:
  timeout_sec: 30
  http_timeout_sec: 5
  report_after_action: false
  only_changed: false
```

`report_after_action` включает отправку состояния сразу после команды,
`only_changed` — фильтрацию неизменившихся значений через кэш рядом с конфигом.
Оба по умолчанию выключены: единственным источником истины остаётся опрос.

Полный пример со всеми параметрами и с закомментированной секцией `devices`
(старый формат привязки) — в `shelly.yaml`.

## Сборка и деплой

```bash
make build                      # в 93.sh
make build-armv7                # под ARMv7
go build -o 94.sh ./cmd/shelly-2.5
```

Рядом с бинарником на сервере должен лежать конфиг с соответствующим именем.

## Проверка

Сухой прогон переключает реле по-настоящему, но вместо отправки в умный дом
печатает то, что ушло бы, — сервер SHS для этого не нужен:

```bash
SHELLY_DRY_RUN=1 ./94.sh $(printf '192.168.20.222|status|' | xxd -p | tr -d '\n')
```

Поэтапный скрипт проверки: связь с реле, модель, режим `relay`, текущее
состояние, сборка и сухой прогон. Переключение он не трогает без флага:

```bash
./test-relay.sh              # только чтение
./test-relay.sh --switch     # плюс вкл/выкл канала 0
```

Тесты:

```bash
go vet ./... && go test -race ./...
```

## Структура

```
cmd/shelly-2.5/                  точка входа, разбор целей, сборка значений
internal/command/                парсинг HEX-команды и адресов назначения
internal/config/                 YAML-конфиг, формы представления значений
internal/shelly/                 REST-клиент Shelly 2.5 (Gen1 API)
internal/reporter/               упаковка и отправка значений в умный дом
internal/statecache/             кэш отправленного, для режима only_changed
internal/transport/api/shClient/ копия клиента протокола SHS
internal/logger/                 настройка zerolog
script/Shelly_2.5.txt            скрипт для умного дома
docs/                            документация языка скриптов и платформы
```

## Коды возврата

| Код | Значение |
|-----|----------|
| 0 | успех |
| 1 | ошибка выполнения: сеть, конфиг, устройство |
| 2 | неверные аргументы или команда |
| 124 | превышен общий таймаут процесса |
